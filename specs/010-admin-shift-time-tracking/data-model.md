# Data Model: Admin-Driven Shift Hours & Extra Hours

**Feature**: 010-admin-shift-time-tracking
**Version**: 1.0
**Date**: 2026-06-05

---

## Summary of Changes

| Entity | Change |
|--------|--------|
| `TimeRecord` | **REMOVED** — manual clock-in/out model deleted (table dropped). |
| `TimeEntry` | **MODIFIED** — `source` enum gains `extra`; `start_time`/`end_time` become nullable; new `note` column. |
| `ShiftRecord` | **UNCHANGED** — kept as the roster assignment / source of shift hours. Legacy `entry_time`/`exit_time` columns are now unused (deprecated). |

---

## Removed Entity: TimeRecord

The `TimeRecord` model (`backend/app/models/time_record.py`) and its `time_record` table are removed entirely. It backed the employee manual clock-in/out flow, which is eliminated. Statistics never depended on it (they derive from `TimeEntry`), so no data migration of historical values is required.

---

## Modified Entity: TimeEntry

### Purpose
Single source of truth for worked hours. Shift hours are auto-generated from assigned shifts (`source="shift"`). Admin/Moderador may add overtime as a separate category (`source="extra"`).

### Field changes

| Field | Before | After | Notes |
|-------|--------|-------|-------|
| `source` | enum `shift` \| `manual` | enum `shift` \| `manual` \| `extra` | `extra` = overtime added by Admin/Moderador. |
| `start_time` | `time`, NOT NULL | `time`, **NULLABLE** | Extra entries have no schedule. |
| `end_time` | `time`, NOT NULL | `time`, **NULLABLE** | Extra entries have no schedule. |
| `note` | — | `str` (≤255), **NULLABLE** | Reason for the extra hours (optional). |

### Unique constraint

`uq_time_entry_employee_date_shift` on `(tenant_id, employee_id, shift_date, shift_type_id)` is **kept**. Extra entries have `shift_type_id = NULL`; PostgreSQL treats NULLs as distinct, so multiple extra entries for the same employee/date are allowed (they sum). Shift idempotency is preserved.

### Validation rules

- `hours_worked` for extra entries: `> 0` and `<= 24` (validated at schema/service layer).
- Extra entries: `source = extra`, `start_time = NULL`, `end_time = NULL`, `shift_type_id = NULL`, `shift_record_id = NULL`.
- Tenant isolation: every query filters by `tenant_id`; extra entries validate the target employee belongs to the caller's tenant.

---

## Statistics impact

Queries that currently filter `source == SHIFT` (employee monthly stats, employee portal stats, department stats) must:

- **Include** `extra` entries in the reported total hours.
- **Report** extra hours **separately** via a new `extra_hours` field, so shift hours and overtime remain distinguishable.

`days_worked` continues to count distinct `shift_date` values with shift entries (extra-only days may be excluded from "days worked" to avoid inflating attendance — documented in the service).

## Alembic Migration

**Migration name**: `remove manual time records, add extra hours to time entries`

Steps (review the autogenerated output by hand — enum changes and table drops usually need manual edits):

1. `DROP TABLE time_record`.
2. `ALTER TABLE time_entries ALTER COLUMN start_time DROP NOT NULL`.
3. `ALTER TABLE time_entries ALTER COLUMN end_time DROP NOT NULL`.
4. `ADD COLUMN note VARCHAR(255) NULL` on `time_entries`.
5. Add `extra` to the `timeentrysource` type. The model uses a non-native enum (`native_enum=False` ⇒ stored as VARCHAR with a CHECK), so this is a CHECK-constraint update rather than `ALTER TYPE`. Adjust accordingly based on the actual column definition.

Downgrade reverses the above (note: dropping a manually-added enum value is non-trivial on native enums; for the non-native/VARCHAR case it is a CHECK-constraint revert).
